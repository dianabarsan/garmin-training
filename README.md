# garmin-training

An MCP server that gives AI assistants read-only access to your Garmin Connect data through
the Garmin Connect Personal API. Connected to Claude or any other Model Context Protocol
client, it lets you query training, sleep and recovery data in natural language, for
example:

- "Compare my sleep this week with last week."
- "List my last five runs with pace and heart rate, and the per-km splits of the longest."
- "Has my resting heart rate or HRV changed since I started this training block?"
- "Summarise this month's strength sessions by exercise."

The server is self-hosted: each user runs their own instance with their own API key.

## How it works

```
 MCP client (e.g. Claude)  ── tool call ──▶  garmin-mcp  ── API request ──▶  Garmin Connect
                           ◀─── result ────              ◀──── data ───────
```

1. Generate a Personal API key in Garmin Connect and provide it to the server.
2. Register the server as a connector in your MCP client.
3. The assistant calls the server's tools as needed, for example to retrieve sleep data for
   a date range. The server fetches the data from Garmin and returns it.

The server is **read-only** and cannot modify your Garmin account. It does not store your
Garmin data; it persists only the API key and, when enabled, an audit log of requests
(never the data returned). The key is
never exposed to the assistant, never logged, and sent only to Garmin.

The Personal API covers an individual's own data. Garmin's terms prohibit its use in
commercial multi-user applications.

## Requirements

- **A Garmin Personal API key**, created at
  <https://connect.garmin.com/app/settings/personalApiToken>. The key is displayed once and
  is valid for a period you choose (30 days to one year). The server exchanges it for
  24-hour access tokens and renews them automatically.
- **An MCP client**, such as Claude Code, or claude.ai and the Claude apps via a custom
  connector.
- **A host for the server.** See [Deployment options](#deployment-options).

## Local setup

Prerequisites: [Docker](https://docs.docker.com/get-docker/), git, curl and bash (macOS,
Linux, or WSL on Windows). The `jq` example below additionally needs
[jq](https://jqlang.org/download/).

```sh
git clone https://github.com/dianabarsan/garmin-training.git
cd garmin-training
./setup.sh
```

The script builds the image, prompts for your Garmin API key (input is hidden), checks it
with Garmin, stores it, and starts the server. If Claude Code is installed, it offers to
register the connector; otherwise it prints the command to do so.

Resulting configuration:

- The server listens on `http://127.0.0.1:8808/mcp`, is reachable only from the local
  machine, and restarts automatically with Docker.
- Clients authenticate with a bearer token, generated by the script and stored in
  `~/.config/garmin-mcp/token`. To connect another MCP client, use the URL above with the
  header `Authorization: Bearer <token>`.
- The API key and the [audit log](#audit-log) are stored in a Docker volume and persist
  across restarts and updates.

| Task | Command |
|---|---|
| Update | `git pull && ./setup.sh` |
| Replace an expired key | `./setup.sh --new-key` |
| View the audit log | `./setup.sh --audit-log` (JSON lines; for example `./setup.sh --audit-log \| jq -c 'select(.msg=="access_denied")'`) |
| Uninstall | `./setup.sh --uninstall` |

## Available tools

All tools are read-only. Dates are local calendar dates (`YYYY-MM-DD`); range tools default
to the last 7 days and accept ranges of up to 366 days.

| Tool | What it returns |
|---|---|
| `list_activities` | Activities with distance, duration, heart rate, elevation, training effect, HR-zone time and, for strength sessions, the per-exercise breakdown. Filters: dates, type, sub-type, text, distance/duration, sort, paging. |
| `get_activity` | One activity's summary. |
| `get_activity_splits` | Per-km (or per-mile) splits computed from the per-second data. |
| `get_activity_series` | Heart rate, speed, elevation, cadence, power over time (GPS is never included), thinned to `max_points`. |
| `get_daily_summaries` | Steps, calories, heart rate, stress, Body Battery, intensity minutes, respiration, SpO2, hydration. |
| `get_sleep` | Sleep stages, score, heart rate, SpO2, sleep need, naps. |
| `get_heart_rate` | Resting/min/max for a day, optionally the curve in buckets. |
| `get_hrv` | Nightly HRV, weekly average, status and baseline. |
| `get_body_battery`, `get_stress`, `get_steps` | Daily series. |
| `get_vo2max` | VO2 max history. |
| `get_heart_rate_zones` | Zones as bpm ranges for a sport. |

Laps and individual strength sets are not available through the Personal API.

If Garmin rejects the key (for example because it expired), every tool returns an error
telling the assistant to ask you to replace it; the assistant cannot do that itself.

### Raw data, location and response size

In addition to the normalised fields above, each item includes Garmin's complete,
unmodified record under `raw`, with fields the normalised output omits (for example an
activity's sensors, lap count or running dynamics). Tools that return raw data accept
`include_raw_data` (default `true`); set it to `false` to return only the normalised
fields. `get_activity_splits` and `get_activity_series` do not include raw data: they are
derived from per-second data, which runs to several megabytes per activity and contains
the full GPS track.

With raw data enabled:

- **Location.** Activity records include start and end coordinates (`startLatitude`,
  `startLongitude`, `endLatitude`, `endLongitude`) and `locationName`. For activities that
  start at home, this discloses your home location to the assistant.
- **Response size.** Responses are several times larger. Measured on a real account:
  7 days of sleep ≈ 50 KB, 7 days of daily summaries ≈ 53 KB, 10 activities ≈ 39 KB, one
  year of sleep ≈ 1.25 MB, which exceeds what an assistant can process at once. For long
  ranges, request shorter periods or set `include_raw_data: false`.

## Privacy and security

The server handles health data and a Garmin credential, and is restrictive by default:

- It binds to loopback and **refuses to start on any other address unless an access token
  is configured**; every client must then present the token.
- The key is given to the server only when it starts, from the environment or a key file.
  There is no endpoint for it, so a leaked access token can neither read nor replace it.
- The API key and the bearer token are never returned by any endpoint or tool, never
  logged, and never included in error messages or the `-h` output. Tests check this.
- An **audit log** records every tool call and refused request (operation, client and time)
  but never the returned data, so access can be reconstructed if a token is compromised.
  See [Audit log](#audit-log).

Full details: [Security model](#security-model).

## Reference

### Providing the key

The server needs a key to start, and reads it once, at startup:

| How | Command |
|---|---|
| Key file (what `setup.sh` does) | `garmin-mcp -set-key -key-store FILE` reads the key from standard input, checks it with Garmin and saves it; then run `garmin-mcp -key-store FILE` |
| Environment | `GARMIN_PERSONAL_API_KEY=... garmin-mcp`, or `GARMIN_PERSONAL_API_KEY_FILE` naming a file that holds it |

The environment wins over the key file. `-set-key` saves a key only if Garmin accepts it;
the file is written with mode `0600` (and its directory, if created, `0700`), and an
existing key file that other users can read is changed to `0600` at startup, with a
warning.

Shortly after starting, the server checks the key with Garmin and logs the result. A
rejected key is not fatal: the server keeps running and every tool says the key must be
replaced. To replace it, save a new one and restart the server (`./setup.sh --new-key`
does both). If Garmin cannot be reached at startup, the key is checked again on the first
request.

### Flags

| Flag / environment | Meaning |
|---|---|
| `-addr` (default `127.0.0.1:8808`) | Address to listen on. |
| `GARMIN_MCP_TOKEN` | Require `Authorization: Bearer <token>` on `/mcp`. At least 16 characters (`openssl rand -hex 32`). There is deliberately no command-line flag for it, where it would be visible in the process list. |
| `-allowed-host` / `GARMIN_MCP_ALLOWED_HOSTS` | Public hostname(s), comma separated, that the server may be reached as. Set it behind a reverse proxy; other `Host` values are refused. On Fly.io, `<FLY_APP_NAME>.fly.dev` is added automatically. |
| `-audit-log` / `GARMIN_MCP_AUDIT_LOG` | Append the audit trail (see below) to this file as JSON lines, mode `0600`. Without it the records appear in the normal log, tagged `audit=true`. |
| `-audit-log-max-mb` (default `10`) | When the audit file would grow past this size it is renamed to `<file>.1`, replacing an older one, and a new file is started. `0` disables the limit; the most allowed is `1048576` (1 TiB). |
| `-key-store` / `GARMIN_MCP_KEY_STORE` | File holding the key, written by `-set-key`. |
| `-set-key` | Read a key from standard input, check it with Garmin, save it to `-key-store` and exit. |
| `-key-stored` | Exit 0 if `-key-store` holds a key, 1 if not. The key is not printed or checked. |
| `GARMIN_PERSONAL_API_KEY` | Key to use (wins over the key store). |
| `GARMIN_MCP_TOKEN_FILE`, `GARMIN_PERSONAL_API_KEY_FILE` | Read the token / key from a file instead (Docker secrets). Setting both forms of one is an error, and so is an empty file, so a failed secret mount never starts the server without a token. |
| `-healthcheck` | Probe a running server at `-addr` and exit 0 if healthy (container health checks). |
| `-log-level` | `debug`, `info`, `warn`, `error`. |
| `-garmin-url` / `GARMIN_PERSONAL_API_BASE_URL` | Garmin base URL (testing). |

### Security model

By default the server is built for a single user on one machine:

- It binds to **loopback** and rejects requests whose `Host` header is not
  `localhost`, `127.0.0.1` or `::1` (DNS-rebinding defence), except `/healthz`, which only answers `ok`.
- State-changing requests carrying a foreign `Origin` or a cross-site `Sec-Fetch-Site`
  are refused (browser CSRF defence).
- It **refuses to start on a non-loopback address without a token** (`GARMIN_MCP_TOKEN`).
- It has no endpoint for the key: the key is read at startup, from the environment or the
  key file, so nothing reachable over HTTP can read or replace it.
- The key is never returned by any tool, never logged, and never part of an error
  message. Tests check this.
- The bearer token is compared in constant time; the `Bearer` scheme is matched without
  regard to case. Request headers are limited to 64 KiB.
- If you expose it beyond localhost, put it behind TLS (a reverse proxy); the server
  speaks plain HTTP. [`docs/fly.md`](docs/fly.md) and [`deploy/README.md`](deploy/README.md)
  both give you HTTPS.

### Audit log

The server records who asked for what, and who was turned away, so you can tell what was
read if a token ever leaks.

| Event | When | Main fields |
|---|---|---|
| `tool_call` | A tool was called | `tool`, `args`, `outcome` (`ok` or `error`), `error`, `duration_ms`, `result_bytes`, `client`, `session` |
| `client_connected` | A client finished the MCP handshake over HTTP | `client`, `session` |
| `access_denied` | A request was refused | `reason` (`missing_token`, `invalid_token`, `forbidden_host`, `cross_origin`), `method`, `path`, `remote`, `forwarded_for`, `user_agent`, plus the `host` or `origin` that was rejected, and `previously_unrecorded` after throttling (below) |
| `access_denied_throttled` | More than 100 requests were refused in a minute; further refusals in that minute are counted, not recorded | `remote`, `forwarded_for` (of the request that hit the limit), `recorded`, `resumes_at` |

Records go into the normal log tagged `audit=true`, or, with `-audit-log path`, into a
separate append-only file of JSON lines (mode `0600`), which is rotated to `<file>.1` at
10 MB (see `-audit-log-max-mb`). Useful filters:

```sh
grep audit=true server.log                                       # the normal log
jq -c 'select(.msg=="access_denied")' audit.log                  # who was refused
jq -c 'select(.msg=="tool_call") | {time, tool, args, client}' audit.log
```

**Where to find it:**

| Setup | Location | Command |
|---|---|---|
| Local, [`setup.sh`](#local-setup) | `/data/audit.log` in the Docker volume (JSON lines), and `/data/audit.log.1` after rotation | `./setup.sh --audit-log` (prints both, oldest first) |
| Local, `go run` or installed command | The server's standard error, or the file passed to `-audit-log` | Read the terminal output, or `jq -c . <file>` |
| Local, systemd ([guide](docs/running-locally.md), section 5) | The user journal, or the file passed to `-audit-log` | `journalctl --user -u garmin-mcp \| grep audit=true` |
| Fly.io ([guide](docs/fly.md)) | Fly's log stream; only a recent window is available | `fly logs -a "$APP" --no-tail \| grep audit=true` (omit `--no-tail` to follow live) |
| Self-hosted server ([guide](deploy/README.md)) | The container log, or a file if configured | `docker compose logs garmin-mcp \| grep audit=true`, run in `deploy/` |

**Never recorded:** the Garmin key, the bearer token (neither the real one nor one a client
presented), or any data a tool returned. `result_bytes` says how much came back, not what.

**What is recorded about requests:** tool arguments are logged because they say what was
read (a date range, an activity id). They can contain free text such as a search term, so
keep the log as private as the data. Values are cut to a fixed length and cannot span
lines. `session` is a short hash of the MCP session id, enough to follow one client's
calls without exposing an identifier that could be replayed.

**Limits:**

- Behind a reverse proxy, `remote` is the proxy's address. `forwarded_for` is the
  `X-Forwarded-For` header exactly as received and a client can forge it, so treat it as a
  hint.
- It is a plain file, not tamper-evident against someone who can write to it. Rotation
  keeps one previous file, so at most about twice the size limit is kept; copy older
  records elsewhere if you need a longer history.
- Refusals are throttled (100 records a minute, from all addresses together, then one
  `access_denied_throttled` record), so a flood of bad requests cannot fill the disk.
  Tool calls are never throttled. During a flood, refusals from other addresses in that
  minute are counted but not recorded; the next record after it gives the count as
  `previously_unrecorded`.
- A `tool_call` is written when the call finishes, so a call that never returns leaves no
  record.
- `client_connected` is only emitted for HTTP clients, which is how real clients connect.

## For developers

The repository holds two Go modules:

- `garmin-connect/` is an importable library for the Personal API, its own module
  `github.com/dianabarsan/garmin-training/garmin-connect` (package `garminconnect`), with
  token handling in `garmin-connect/auth`. It depends on the standard library only, so
  importing it adds nothing else to your module graph, and it needs Go 1.24 or later.
- The repository root is the MCP server's module. `cmd/garmin-mcp/` holds the `main`
  package (configuration, logging, listening and shutdown) and `internal/mcpserver` (the
  tools and HTTP routes). It requires a tagged version of the library and is the only place
  that uses a third-party module (the official MCP Go SDK).

The committed `go.work` makes the go command build the server against the library in this
repository, so a change to both can be made and tested together. `go install` and anyone
importing the modules ignore it.

### Using the library

```go
import (
	garminconnect "github.com/dianabarsan/garmin-training/garmin-connect"
	"github.com/dianabarsan/garmin-training/garmin-connect/auth"
)

ts := auth.NewTokenSource(os.Getenv("GARMIN_PERSONAL_API_KEY"))
c := garminconnect.New(garminconnect.WithTokenSource(ts))

acts, err := c.Activities(ctx, garminconnect.ActivitiesOptions{SubTypeKey: "strength_training", Limit: 5})
if err != nil {
	return err
}
if len(acts) == 0 {
	return nil // no strength workouts yet
}
series, err := c.ActivitySeries(ctx, acts[0].ID)
if err != nil {
	return err
}
splits, err := series.Splits(1000)
```

It covers activities (list, paging, filters, detail, FIT download, per-second series,
splits, strength breakdown), daily summaries, steps, stress, sleep, heart rate, HRV,
Body Battery, VO2 max and heart-rate zones.

Behaviour worth knowing:

- **Dates** are formatted in the `time.Time`'s own location, so pass dates in the user's
  time zone (`time.Now()` in UTC can be a different calendar day).
- **Long date ranges** are split automatically to fit Garmin's per-endpoint caps, up to
  `MaxRangeDays` (about ten years). If a later request fails, the results fetched so far
  are returned along with the error.
- **No data** (HTTP 204, or a JSON `null`) is an empty result, not an error.
- **Errors** match sentinels with `errors.Is`: `ErrUnauthorized`, `ErrForbidden`,
  `ErrNotFound`, `ErrBadRequest`, `ErrRateLimited`, `ErrServer`, and others listed in the
  package documentation. `*APIError` carries the status code.
- **Timeouts and retries:** requests have no overall timeout, so bound them with your
  context. Each attempt is limited instead (`WithAttemptTimeout`, default 30 s for the
  headers and for any gap in the body), and timeouts, dropped connections, 429 and most 5xx
  responses are retried with backoff (`WithRetry`). A download (`DownloadActivity`) that
  stalls part way is not retried, since part of it is already written; it fails with
  `ErrAttemptTimeout`.
- **Revoked tokens:** a 401 is retried once with a fresh token when the token source
  implements `TokenInvalidator`, as `auth.TokenSource` does. This happens at most once a
  minute, so an endpoint that keeps refusing does not cost a key exchange per request.
- **Limits:** JSON responses are capped at 64 MB (`WithMaxResponseBytes`).
  `DownloadActivity` streams to your writer and is not capped. Base URLs must use https,
  except for a local test server.
- **Models are for decoding.** Encoding one to JSON does not reproduce Garmin's format;
  keep `Raw()` to store or forward a response.

### Development

Run the checks in both modules:

```sh
go vet ./... && go test -race -cover ./...                                    # the server
(cd garmin-connect && go vet ./... && go test -race -cover ./...)             # the library
```

Live checks against your own account are behind the `live` build tag and read the key
from a file named `key` in the repository root (git-ignored):

```sh
go test -tags live -run TestLive -v ./cmd/garmin-mcp                     # the server, every tool
(cd garmin-connect && go test -tags live -run TestLiveTyped -v .)        # the library
```

`garmin-connect/testdata/shapes/` holds the structure of real responses with every value blanked.
`garmin-connect/testdata/live/` (git-ignored) is where raw captures go; it can contain GPS and health
data and must not be committed.

### Releasing

The library is tagged `garmin-connect/vX.Y.Z` and the server `vX.Y.Z`. The server's
`go.mod` must require a library version that has been tagged, so a release that changes
the library takes two steps:

1. Tag and push the library: `git tag garmin-connect/vX.Y.Z && git push origin garmin-connect/vX.Y.Z`.
2. Require it in the root `go.mod`, record its checksums without the workspace, then
   commit, tag and push the server:

   ```sh
   go mod edit -require=github.com/dianabarsan/garmin-training/garmin-connect@vX.Y.Z
   GOWORK=off go mod tidy && GOWORK=off go build ./...
   ```

   Then change the version in the `replace` line of `go.work` to match.

Until the first library tag (`garmin-connect/v0.1.0`) exists, the server builds only
inside the workspace.
